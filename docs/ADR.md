# Architecture Decision Records

Decisions that shape HDD across its roadmap. Each one records what was decided, why, what
it costs, and what was rejected. **Read this before changing the data layer, the IPC
contract, or the way the UI talks to the main process.**

Format: Status / Context / Decision / Consequences / Alternatives.

Statuses: `Accepted`, `Superseded by ADR-NNN`, `Proposed`.

---

## ADR-001 — The main process owns the truth

**Status:** Accepted

**Context**

The renderer currently keeps the conversation in a local `history` array and sends the
whole thing to the main process on every turn. That works for a single-session demo. It
does not survive Phase 2 (topics, switching, full-text search), Phase 3 (long-term
memory), Phase 4 (context assembly) or Phase 8 (multi-step execution), because all of
those need an authoritative, persistent conversation state that outlives the window.

The main process already holds the API key and is the only layer allowed to touch the
network, so it is already the application's trusted core.

**Decision**

The main process is the single source of truth for all persistent state: messages,
topics, the user profile, memories, files and tool results. The renderer becomes a
**display layer plus input**, holding no authoritative state.

The IPC contract therefore becomes conversation-oriented rather than stateless:

```
renderer  -> sendUserMessage(text)     // one message, not the whole history
main      -> stream(reasoning|content|done|error, turnId)
renderer  -> listMessages({ topicId, limit })   // on startup, to repaint
```

**Consequences**

- The renderer can be replaced (or a web client added) without migrating data.
- The renderer cannot persist anything itself; every write goes through the main process.
- `history` disappears from `live.template.html`; the renderer asks for what to draw.
- Per-turn history trimming moves into the main process next to the data.

**Alternatives rejected**

- *Keep state in the renderer, persist via `localStorage`*: the renderer is sandboxed with
  a network-blocking CSP, and `app/www/` is regenerated by `prep` on every build, so
  anything stored there is destroyed on the next build.
- *Keep state in the renderer, persist via a preload file API*: two sources of truth
  (renderer array and file) that drift, and every read/write becomes a round trip anyway.

## ADR-002 — SQLite via the built-in `node:sqlite`, not JSON files

**Status:** Accepted

**Context**

Phase 2 needs full-text search and topics; Phase 3 needs structured, updatable memories;
Phase 5 needs embeddings. A flat JSON or JSON-lines store forces a data migration at
Phase 2 — after real conversations exist, which is the worst time to migrate.

`better-sqlite3` would solve that but is a native module, which forces an
`electron-rebuild` step; that step has already been a build blocker in this project
(`spawn EPERM`), and `npmRebuild` is currently disabled for exactly that reason.

Verified in this environment: Electron 44.3.0 ships Node 24.20.0, and
`require('node:sqlite')` works **inside the Electron main process**, with **FTS5 compiled
in** (a `CREATE VIRTUAL TABLE ... USING fts5` query matched successfully).

**Decision**

Use `node:sqlite` (Node's built-in SQLite) in the main process.

- No new dependency, no native compilation, no rebuild step.
- FTS5 external-content tables for full-text search from Phase 2.
- Transactions for crash safety.

**Consequence discovered during implementation: CJK needs a custom index field.**

FTS5's `unicode61` tokenizer treats a whole run of Chinese as one token, so searching for
a two-character word inside a longer sentence returns nothing. The `trigram` tokenizer
only matches 3+ characters, which excludes the two-character words that dominate Chinese
queries.

So `messages_fts` stores a second, pre-tokenized copy of each message in a `tok` column:
CJK characters separated one per token, Latin words left whole. Queries go through the
same transformation and are ANDed, so adjacent tokens behave like a phrase. Verified
against the real database with two-character words, single characters, longer phrases and
Latin words — all match, and unrelated text does not.

This is the kind of thing that would have been a data migration had it been discovered in
Phase 2 (see ADR-004). Any future search feature must go through `toMatchQuery` rather
than passing raw user input to `MATCH`.

**Consequences**

- The database is a binary file; inspecting it needs a tool. Mitigation: provide an export
  command that dumps human-readable JSON, so the data stays auditable.
- `node:sqlite` is a relatively new Node API; pin the Electron major version and re-verify
  FTS5 after any Electron upgrade.
- Vector search (Phase 5) will still need an extension (`sqlite-vec` or similar); that
  decision is deferred to ADR-007.

**Alternatives rejected**

- *JSON Lines*: simplest, but guarantees a storage rewrite at Phase 2, and every update
  rewrites more than it needs to.
- *Single JSON document*: rewrites the whole file on every message; one corrupt write
  loses everything.
- *`better-sqlite3`*: same SQL, but reintroduces the native-rebuild problem.
- *LowDB / LevelDB / etc.*: still no query language, still no FTS.

## ADR-003 — State lives in `app/data/`, outside `app/www/`

**Status:** Accepted

**Context**

`app/www/` is generated by `scripts/prep.cjs` and wiped/rebuilt on every build, and is
gitignored. Anything persisted there is destroyed by a rebuild.

**Decision**

Persistent state lives in `app/data/` (gitignored): `hdd.db`, plus exports.

**Consequences**

- The portable exe unpacks itself into `%TEMP%` on every launch, so state written next to
  the running app would be destroyed. This is the same constraint that already stops a
  portable exe from reading a `config.json` placed beside it (see README 3.1).
- **Consequence for packaged builds (implemented):** `app/data/` inside the asar is
  read-only, so a packaged app resolves its data directory to a writable per-user location
  instead: `getDataDir()` returns `app.getPath('userData')/data` when
  `app.isPackaged`, and the directory is created on first open. Precedence is
  explicit `dir` argument → `HDD_DATA_DIR` → `userData` (packaged) → `app/data`
  (development). The packaged branch is not covered by the automated tests, which run
  outside Electron; it is verified by running a built exe once and confirming
  `%APPDATA%\HDD\data\hdd.db` appears.

**Alternatives rejected**

- *`app/www/data/`*: destroyed by `prep`.
- *Beside the executable*: impossible for a portable build (unpacked to `%TEMP%`), and
  often unwritable under `Program Files`.
- *Inside the asar*: read-only.

## ADR-004 — Schema migrations from day one

**Status:** Accepted

**Context**

The roadmap has nine phases and nearly every one adds tables or columns: topics (Phase 2),
memories (Phase 3), projects and context (Phase 4), files and chunks (Phase 5), tool
invocations (Phase 6), tasks and reminders (Phase 7), agent runs (Phase 8 — removed by
ADR-015), schedules (Phase 9). Without a migration mechanism every addition becomes a manual
database edit or a data-losing rebuild.

**Decision**

A `schema_version` table plus an ordered list of migrations, applied on startup inside a
transaction. Never edit a shipped migration; always append a new one.

**Consequences**

- Adding a table or column is a one-line append.
- Downgrades are not supported; a newer schema opened by an older build must fail loudly
  rather than silently corrupt.
- Migrations must be idempotent-safe to re-run after a crash mid-migration (wrap in a
  transaction; SQLite DDL is transactional).

**Alternatives rejected**

- *`CREATE TABLE IF NOT EXISTS` everywhere*: cannot express `ALTER TABLE`, cannot backfill,
  and gives no way to tell whether a shape change actually applied.

## ADR-005 — Stable IDs and UTC timestamps

**Status:** Accepted

**Context**

Phase 2 tags messages with topics, Phase 3 links memories to their source messages,
Phase 4 links topics to projects, Phase 6 links tool calls to turns, Phase 8 links agent
steps to runs. All of that is foreign keys. Auto-increment rowids are fragile across
exports, merges and re-imports, and Phase 9 (scheduled tasks, weekly reports) will be
painful if times are stored ambiguously.

**Decision**

- Every entity has a stable, application-generated string ID (time-sortable, e.g.
  `<unix-ms>-<random>`). Never expose raw rowids as identity.
- Timestamps are stored as **UTC epoch milliseconds** (integer). Formatting to local time
  happens only at display time.
- Chronological ordering uses `(created_at, id)` so equal timestamps stay deterministic.

**Consequences**

- IDs are opaque but stable; they survive export/import and can be referenced in logs.
- Never store pre-formatted local time strings as the source of truth.

## ADR-006 — No topics table in v0.1, but the schema must allow it

**Status:** Accepted

**Context**

Phase 2 introduces topic detection, creation and switching. Phase 1 does not need topics.
Adding a `NOT NULL` topic reference later would require backfilling every existing message.

**Decision**

v0.1 stores a single implicit conversation. The `messages` table ships **without** a topic
column, and the Phase 2 migration adds `topic_id` as **nullable**, then backfills.

**Consequences**

- Phase 2 is an additive migration, not a rewrite.
- Do not scatter assumptions of "one conversation" through the code; keep conversation
  selection behind a single accessor so a topic parameter can be threaded through later.

**Implemented in Phase 2 as migration 3** (`topics` + nullable `messages.topic_id` + index), with
`backfillTopics()` turning what was the single implicit conversation into exactly one topic. The
policy that fills the column afterwards — when a boundary occurs, what a topic does to the
prompt, and how it is driven — is ADR-012. The accessor this ADR asked for is
`store.recentMessages(db, limit, { topicId })` plus `conversation.listHistory({ topicId })`.

**Alternatives rejected**

- *Add `topic_id` in v0.1 with a hardcoded default*: premature, and the default topic row
  would still need a migration to become meaningful.

## ADR-007 — Embeddings and vector search are deferred to Phase 5

**Status:** Proposed (decide when Phase 5 starts)

**Context**

Phase 5 needs document chunking, embeddings and semantic retrieval. Phase 2 only needs
full-text search, which FTS5 already provides. Choosing a vector store now would be a
guess made without knowing the chunk volume, the embedding model or the query patterns.

**Decision**

Do not add a vector store in v0.1. Keep the storage layer behind a small module API so the
retrieval backend can be swapped.

**Consequences**

- Phase 2's "semantic search" item depends on this decision; if Phase 2 really needs
  semantics (not just FTS), revisit here before starting it.
- Options to evaluate at Phase 5: `sqlite-vec` (keeps one database), a separate vector
  store, or FTS5 plus a re-ranking step if the data set stays small.

## ADR-008 — Persona lives in code, prompt is assembled per turn

**Status:** Accepted

**Context**

`app/personality.js` holds the persona and few-shot examples; `prep.cjs` embeds them into
the page as JSON (so quotes and newlines in the prompt cannot break the inline script).
The system prompt is rebuilt every turn to include the current time.

**Decision**

Keep the persona as source code in the repository, assembled per turn, with a stated
**precedence order** when guidance conflicts:

```
1. safety and honesty   (capability boundary, never fake an action)
2. identity             (she is Fairy)
3. user-state fit       (do not joke when the user is distressed)
4. style                (cold humour, vanity, teasing)   <- always last
```

**Consequences**

- Style can never override honesty or the user's state; this is what makes her behaviour
  consistent rather than merely colourful.
- The prompt is well under 1k tokens per turn. If memory and context layers grow it,
  revisit: a static persona block should not be re-sent verbatim forever (cache it, or
  split stable from dynamic parts).

**Current scope — deliberately minimal persona**

The full character (cold humour, vanity, teasing, the precedence levels 3 and 4 above) is
**not** in this build. Until v1.0 the persona carries only what a build with no tools, no
memory beyond recent turns and no perception actually needs:

1. identity — she is Fairy, never another model's name;
2. honesty — one line: never invent a completed action (the *facts* about what the program
   can do are not persona material; they live in `capabilities.js`, see ADR-009);
3. speech rules —「主人」, one line per reply, no emoji, no invented actions.

Writing the rest now would mean describing capabilities that do not exist yet, which
ADR-009 forbids: a character defined by what she can do cannot be written before she can do
it. The few-shot example mechanism is retained in `personality.js` as an **empty array** —
the injection path is tested, so v1.0 only has to fill the list.

The style examples, when they return, must stay in the system prompt as labelled fiction.
Injecting them as `user`/`assistant` message pairs was tried and reverted: the model read
them as real history and answered the examples instead of the user.

**Alternatives rejected**

- *Fine-tuning the persona*: expensive, slow to iterate, and cannot be inspected or edited
  in a text editor.
- *Storing the persona only in the database*: makes the character unreviewable in version
  control and un-reviewable in a diff.

## ADR-009 — Claim no capability the app does not have

**Status:** Accepted

**Context**

The original persona design asserted camera access and hardware sensing and required the
model to insist it could see the user. HDD has neither. Carrying those claims over would
make the model invent results — which the same design's own "never fake an action" rule
forbids.

**Decision**

The prompt states, explicitly, what the app cannot do, and the persona forbids claiming
otherwise.

**Revised twice (still Accepted, same decision, different expression).**

*Revision 1 — the facts left the persona.* The capability list was originally prose inside
`personality.js`. That was a layering mistake: reading as character, it looked like fair game
for a tone edit — and one did delete the entire boundary, turning five assertions red without
anyone touching a guarantee. Taste and correctness should not share a string. Facts moved to
`app/capabilities.js`, rendered into the prompt every turn by `conversation.js` beside the
profile and the current time; the honesty *disposition* stayed in the persona as one line.

*Revision 2 — the absences are no longer rendered.* Revision 1 rendered both lists, including
a bulleted "cannot" section. A real conversation then showed the model reading that section
straight back at the user:

> 我只能做两件事：和你文字对话，以及知道当前日期时间。做不到的有：看摄像头、读硬件状态、
> 替你操作电脑或发消息、读写文件、上网搜索。所以帮不了你查东西、定闹钟或放音乐。

An assistant reciting an inventory of its own limitations is wrong twice over: it is not how
anyone describes themselves, and naming the absences primes those exact tokens (camera, music,
alarms), making her more likely to talk about — or improvise around — the very things she must
not promise. So the prompt renders **only** what she can do. `CANNOT_DO` is kept in
`capabilities.js` as data that is deliberately **not** rendered, for three reasons: the test
that forbids a denial list in the prompt uses it as its fixture, the cross-checks name it, and
whoever adds a capability should see what was already considered.

*Revision 3 — completeness is not claimed either.* Revision 2 still declared that the list was
the whole of it, so the absences could be derived by subtraction. Asked what she could do, she
answered "我能陪主人文字对话，也知道当前的日期和时间。就这些。" Removing the claim helped but
did not settle it — "就这些" still appeared in one run out of three, so it is also the model's
own habit of closing a short enumeration. The block is now a heading and two bullets, and the
persona carries a manner rule against announcing completeness in any wording (naming specific
phrases only produced a synonym: "就这样"). Six consecutive runs after the change ended
cleanly.

That completeness was not load-bearing for honesty is the useful finding here: the guarantee
rests on the honesty rule, not on the prompt telling her its list is exhaustive. Five questions
written to invite a fabricated "已经为您做好了" — search the web, read my screen, rename a file,
set an alarm, read my expression — were each refused plainly with the completeness claim absent.

The persona carries the manner rules, because they are about tone: state only what you can do
and stop; when a request hits a limit, name that one thing and offer what you can do instead.

Precedence in the prompt is persona → capabilities → profile → time, so the facts sit
immediately after the character rather than buried under flavour.

**Verified by behaviour, not only by assertion.** Four probes through the real assembly path:
"你能帮我做什么" answers in one sentence with no list; "帮我看看我现在的表情", "帮我放首歌"
and "把这个对话存成文件吧" each name the single relevant limit and invent nothing.

**Consequences**

- Adding a real capability is a change to `capabilities.js` alone. The cross-checks then fail
  until the declaration matches reality again, so a capability cannot be added silently — nor
  left falsely denied.
- Phase 6 should generate the tool entry from the actual tool registry rather than
  hand-maintaining it; the cross-check is the interim guarantee.
- The model cannot introspect its own host: it cannot notice a missing camera, and it cannot
  try and fail. Capability awareness is injected state. The improvement here is which layer
  injects it, not that it is no longer injected.
- **Do not turn the absences back into a list.** That is now enforced by a test, not by this
  paragraph. If she starts promising something she cannot do, the fix is a sharper positive
  statement or a sharper manner rule — not an inventory of refusals.

## ADR-010 — Behaviour quality gets an evaluation set, features do not get one

**Status:** Accepted — started during Phase 2, and its first entry is a real transcript

**Context**

From Phase 2 onward the hard problems are behavioural, not structural: is the topic
detection right, did the memory extractor pick the right fact, should the agent have acted
autonomously. These are tuning problems. Without a fixed set of cases and a recorded
judgement, every change is a guess and regressions are invisible.

**Decision**

Maintain a small evaluation set: real conversation snippets plus a written expectation for
each. Grow it opportunistically — whenever behaviour is wrong, add the case. Scoring may
start as a manual pass before any automated judge is introduced.

**Consequences**

- Costs almost nothing to start and is expensive to reconstruct later.
- An automated judge (a second model grading responses) is a later, optional upgrade, and
  costs API credits; the manual set is the prerequisite for it.

**How it works in practice.** Entries live as data in `docs/eval/*.json`, and
`tests/conversation.test.cjs` replays them: the recorded human judgement is supplied as the
confirmer's answer, and the test asserts everything *except* the model's own quality — which
turns were proposed, where each message landed, what history each turn received. The model's
answer is the thing under evaluation, so it stays data rather than becoming an implementation
detail. Adding a case is appending a turn and a judgement, not writing an assertion.

**First entry: `docs/eval/topics-2026-09-14.json`.** The conversation that broke revision 0 of
ADR-012, kept verbatim. It is the reason that ADR has a revision, and it is the reason this
one moved from Proposed to Accepted: the set did not just cost nothing to start, it found a
defect on its first real use.

## ADR-011 — Licensing and secrets constrain the build

**Status:** Accepted

**Context**

The visual assets derive from Fairy-DSH (Apache-2.0). The repository must not ship a font
it may not redistribute, and a distributed build must not contain the developer's API key.

**Decision**

- **Fonts are not committed.** `.gitignore` excludes `app/fonts/*.ttf|otf|woff|woff2`;
  `prep.cjs` registers whatever is present and the UI falls back to a system font otherwise.
- **Published builds do not embed the font either.** Not committing a font is not enough:
  `www/**/*` goes into the asar, so anything in `app/fonts/` was being redistributed inside
  every exe. `release.ps1` sets `HDD_NO_FONTS=1` for the build; `prep.cjs` then skips font
  registration entirely, leaving no `@font-face` and no font bytes, and the artifact check
  fails if any font file is found in the asar. A local `npm run dist` still embeds it, which
  is what the developer wants on their own machine.
- **`app/config.json` is never committed** (it holds the API key).
- **Published builds are built with the placeholder key** from `config.example.json`.
  `release.ps1` performs this swap, restores the real config in a `finally` block, and
  verifies the packaged asar contains no real key.
- `THIRD_PARTY_NOTICES.md` and `LICENSE`/`NOTICE` must keep travelling with the project.

**Consequences**

- A distributed binary is always key-free; users supply their own key via the environment
  or `config.json`.
- Do not add a dependency without recording it in `THIRD_PARTY_NOTICES.md`.

## ADR-012 — Topics: a local boundary decision, scoped context, derived titles

**Status:** Accepted

**Context**

Phase 2 needs topic detection, creation and switching (ROADMAP), and ADR-006 already committed
to the schema shape: a `topics` table, `messages.topic_id` added **nullable**, then backfilled.
Four questions were left open, and each of them could have gone at least two ways:

1. **Where does a boundary come from?** The model could be asked "is this a new subject, and
   what would you call it" — accurate and expensive — or the app could decide locally from
   signals it already stores.
2. **What does a topic do to the prompt?** It can be a label over a global history, or it can
   select the history.
3. **Where do titles come from?** Generating one costs a request; deriving one is free and
   deterministic.
4. **How is it driven?** The terminal has one input line and no chrome.

ADR-010 says the hard Phase 2 problem is behavioural and needs an evaluation set; ADR-007 defers
semantics to Phase 5, so "semantic search" is explicitly out of scope here.

**Decision**

**1. The boundary is decided locally, in `app/topics.js`, with no extra request.** Two signals,
both already in the store, and a message must be *substantial* before either is trusted:

- **substance** — at least `MIN_TERMS_TO_JUDGE` (8) distinct content terms, where a term is a CJK
  bigram or a whole Latin word with common function words removed. Below that the message stays
  where it is, whatever it says.
- **coverage** — the share of the message's content terms that already appear in the current
  topic's last `RECENT_WINDOW_MESSAGES` (8) messages. Below `SHIFT_COVERAGE` (0.05) the subject
  has clearly changed; after `IDLE_GAP_MS` (6 h) of silence the same test is applied with a lower
  bar, `IDLE_COVERAGE` (0.2), which is what a "new sitting" adds.

`decideBoundary` returns `first | idle | shift | continue`, and the reason is kept on the turn.
It is how a wrong boundary is diagnosed, and it is what the evaluation cases assert.

CJK bigrams, not the single characters the FTS index uses: 的 / 我 / 不 appear in unrelated
sentences, so single characters report continuity between subjects that share nothing.

**2. Topics select context.** The message being answered is filed into its topic, and the history
sent to the model is that topic's history. The profile (first meeting, turns) stays global —
those are facts about the relationship, not about a subject. Switching topics therefore changes
what she is reminded of, which is the only thing that makes switching mean anything.

**3. Titles are derived from the message that opened the topic** (`titleFromText`, truncated at
`TITLE_MAX_CHARS` = 24 with an ellipsis, `未命名话题` when there is nothing to derive from), and
renamable with `/rename`. A generated title would cost a request and buy wording, and the title
is a label in a list, not part of the persona.

**4. The detector is overridable, and that is a requirement rather than a courtesy.** Lexical
overlap cannot see a subject continued in entirely different words; the measurement below says
so. `/new` and `/switch` are the escape hatch, which is why an explicitly created empty topic is
never abandoned by the detector.

**5. Migration 3 is additive and the backfill is one topic.** `topics` is created,
`messages.topic_id` is added nullable with an index, and `backfillTopics()` puts every
pre-existing message into a single topic titled from the earliest user message. Re-segmenting
that history with the detector was rejected: it would guess at boundaries nobody recorded, and it
would make the upgrade unreproducible — your topic layout would depend on *when* you upgraded.

**6. It is driven by slash commands on the existing input line** (`/topics`, `/switch`, `/new`,
`/rename`, `/search`, `/help`). They print through the same `.line` elements as everything else,
so no CSS, mask, weight or scroll behaviour changes. A topic list panel is a separate visual
design and stayed deferred.

**Consequences**

- **The constants were measured, not guessed, and they are still provisional.** They were fixed
  against labelled exchanges, and the first guess was wrong in a way worth recording: at
  `MIN_TERMS_TO_JUDGE = 3` and `SHIFT_COVERAGE = 0.12`, three of four connected short exchanges
  in a row were split into separate topics. The two mistakes are not equally bad — a **false
  split** hands the next turn a prompt missing the subject it belongs to, so she appears to have
  forgotten the conversation (exactly the failure `COMMANDS.md` §8 tells you to debug with
  `inspect`), while a **missed split** only groups a few unrelated messages together, which
  search survives. So the constants bias toward continuing: every observed false split sat at 7
  terms or fewer and the shortest genuine change of subject worth catching carries 8.
- **The price is explicit**: a short request that really does start a new subject ("推荐几部电影",
  5–6 terms) is merged into the current topic. `/new` states the intent instead. This is the
  first thing the evaluation set should revisit.
- Titles and boundaries are reproducible offline, so the whole policy is covered by plain Node
  tests; the seed cases live in `tests/conversation.test.cjs` §9.
- `inspect.cjs` prints the topic of every message and scopes `--prompt` to the topic in progress,
  because a boundary in the wrong place is invisible on screen and obvious in the prompt.
- **The IPC surface grew by five channels, so it is now cross-checked statically**: every channel
  `preload.cjs` uses must be registered in `main.js`, and every `api.*` the page calls must be
  exposed by the preload. The renderer tests replace the real bridge with a fake, so without that
  check a typo in a channel name would have shown up only as a command that does nothing in a
  real window. The check was verified by breaking it.
- Capability facts are untouched: topics are not a capability and the persona does not mention
  them (ADR-009).

**Two defects the implementation produced, both caught before release**

1. **An explicitly created empty topic was immediately abandoned.** The detector judged the first
   message of a fresh topic against *no* subject at all, scored it as completely off-topic, and
   created a second topic beside the empty one — so `/new` followed by anything substantial could
   never work. Fixed by treating "the current topic has no messages yet" as a continuation: an
   empty topic is waiting for its first message, whoever created it.
2. **Detection and message timestamps read the clock separately.** The topic decision used the
   conversation's clock while `appendMessage` stamped rows with the wall clock, so in a test with
   an injected clock the idle gap computed as *negative* and the idle rule silently never fired.
   The turn now takes one reading and uses it for both, which is also correct in production: two
   readings can land either side of the threshold.

**Alternatives rejected**

- *Ask the model whether the subject changed*: better boundaries and better titles, but a request
  per turn, unusable offline, and it would make ADR-010's tuning loop depend on API credits. The
  signals it would use are already stored locally.
- *Semantic similarity for the boundary*: needs embeddings, which is ADR-007's Phase 5 decision.
  Revisit together with it — this is the obvious upgrade path for the paraphrase failure.
- *Split one topic per message, or per day*: meaningless as subjects and destroys search.
- *Re-segment existing history at upgrade* (see decision 5).
- *A topic list panel or sidebar*: a visual change to a verified fullscreen layout, for a feature
  that six commands already cover. Deferred, not rejected (see the deferred table).
- *`topic_id NOT NULL` with a default row*: rejected already in ADR-006, and it would put a fake
  topic in every store that never used topics.

| --- | --- | --- | --- | --- |
| 那个终端项目的全文搜索做到哪一步了 | 15 | 0.333 | continue | continue |
| 中文分词你是怎么处理的… | 15 | 0.000 | **split** | same subject |
| 我想给这个软件再加点本事… | 21 | 0.000 | **split** | same subject |
| 给我推荐几部科幻电影吧… | 19 | 0.000 | split | new subject |
| 附近有什么好吃的 | 6 | 0.000 | continue | new subject |

A continuation and a change of subject both scored **0.000**, and their term counts
**interleaved** (false splits at 15 and 21, real splits at 17 and 19). No value of either
constant separates those cases, so the tuning described under "Consequences" below could never
have worked: it was the wrong axis, not the wrong number.

Two further findings made the failure serious rather than untidy.

**A false split changes what the user's sentence means.** With `historyBefore` empty,
"中文分词你是怎么处理的" stopped meaning *how does your project handle Chinese tokenization* and
became *how do you yourself tokenize*; she answered about her own tokenizer. "我想给这个软件再
加点本事" stopped meaning *add a feature to my app* and became *modify yourself*; she answered
that she cannot change her own code. Being handed no context does not just lose information — it
reinterprets the question.

**The tuning was fitted to a distribution that does not exist.** The cases revision 0 was tuned
on were written by the developer, and in every one of them the assistant reply cooperatively
echoed the user's vocabulary — which is the only bridge the metric has. Real replies refuse and
pivot: asked about search progress, she replied *"我这边没有那个项目的记录…你想聊哪一块，
schema、迁移还是查询封装？"* and never said 中文分词. The bridge the rule relied on was absent in
production. A metric fitted on invented replies to invented questions measured the invention.

So the roles changed:

- **`proposeBoundary` (was `decideBoundary`) only proposes.** It is tuned for **recall**:
  `MIN_PROPOSAL_TERMS` dropped 8 → **5** and `PROPOSE_COVERAGE` 0.05 → **0.15**, because a
  proposal that is wrong now costs one small request, while a proposal that is missing costs a
  subject that never gets its own topic. `IDLE_COVERAGE` widened 0.2 → **0.35** for the same
  reason.
- **A boundary is opened only when the confirmer says so** — a small non-streaming request
  (`confirmBoundary` in `main.js`) that answers `{same, title}`. It also **names** the topic,
  which retires the "title is a truncated sentence" problem: `给我推荐几部科幻电影吧，最好是硬科幻
  那种，别太商…` becomes a noun phrase.
- **Anything other than an explicit "yes" keeps the message where it is.** A missing key, a
  timeout, a parse failure, a thrown error and an explicit "same" are all one outcome: stay. A
  classifier that cannot answer must not be able to invent boundaries, so `topics.js` without a
  confirmer behaves exactly like the "one topic per sitting" fallback that was the alternative
  to this design. That is asserted in `conversation.test.cjs` §10b.
- **Cost, stated plainly:** one extra request on each proposed turn — turns whose message shares
  no vocabulary with the current subject — and the latency of that request before the reply
  starts. In the transcript that was 5 of 8 turns. It buys boundaries that are actually right,
  and the title. Changing this is a change to `docs/ADR.md` and `RELEASE_NOTES.md`, not a
  preference: revision 0's "no extra request" is withdrawn.

**Titles became a separate, smaller problem.** A session opens with a greeting, so the topic it
creates is named "你好" and should not keep that name. Migration 4 adds `title_locked`: a title
is provisional until the user renames it or a message substantial enough to name a subject
arrives. A topic that is still provisional when a confirmed boundary happens is **absorbed** into
the new topic rather than left behind, so a sitting does not accumulate one nameless topic per
greeting. A migrated v0.1 topic is locked at backfill: its title comes from a whole conversation,
and re-deriving it from whichever message arrives next would mislabel hundreds of messages.

**The measurement to make next.** The confirmer's own quality is now the open question, and it is
the one thing that cannot be asserted offline: `docs/eval` records the human judgement per turn
and the tests replay it as the confirmer's answer, which verifies everything *except* whether the
model agrees. Evaluating the model means running the real conversation again and comparing its
verdicts against the recorded ones.

**Three defects this revision's own implementation produced, all caught by tests before release**

1. **Any message could name a topic.** The provisional-title path ran for every message, not just
   substantial ones, so a two-term laugh retitled a greeting topic to "哈哈哈" — and because
   naming locks the title, it also blocked that topic from being absorbed. The rule is now that a
   message can only name a topic if it could have named it in the first place.
2. **An explicitly created empty topic was abandoned by the detector** (revision 0's defect,
   kept here because the fix is what makes `/new` usable).
3. **The boundary decision and the message timestamps read the clock separately**, which made the
   idle rule silently never fire under an injected clock.

**Alternatives rejected**

- *Keeping revision 0 and tuning further*: no value of either constant separates the cases in the
  table above. Measured, not argued.
- *Embeddings for the boundary*: still the right long-term answer, still ADR-007's Phase 5
  decision, and the natural replacement for the confirmer when it lands.
- *One topic per sitting* (the fallback this revision degrades to): it never misleads, but it does
  not deliver topic detection either. It is now the failure mode rather than the design.
- *Asking the confirmer on every turn*: doubles the request count to catch a boundary the local
  rule would have proposed anyway.

**Revision 2 — one shared term is a coincidence, not a shared subject.**

The second real conversation ran with the confirmer live, and it produced two results that point
in opposite directions. It is kept as `docs/eval/topics-2026-09-14-run2.json`.

**The confirmer works.** The topic came out of that run named 「电影推荐」 — a noun phrase, from
the model, which means the request was made, answered, parsed and used. Revision 1's central
mechanism is no longer a hypothesis.

**The proposer was wrong twice, and the model was never asked either time.**

| turn | terms | shared with the topic | coverage | revision 1 said | actually |
| --- | --- | --- | --- | --- | --- |
| 附近有什么好吃的？ | 6 | **1** — 「有什」 | 0.167 | continue | new subject |
| 上学好烦啊 | 4 | 0 | 0.000 | *below the floor* | new subject |

The first is the more interesting failure. Its entire lexical link to the topic was 「有什」, a
bigram spanning 有|什么, matched against the greeting's 「有什么事？」. Two characters that mean
nothing together produced a coverage of 0.167, which cleared the 0.15 bar and suppressed the
question. The second is simpler: four content terms fell below a floor of five, so a short,
unambiguous change of subject was never considered.

So the local rule gained the two conditions it was missing:

- **`MIN_SHARED_TERMS` = 2.** A message can only be treated as plainly on-topic when it shares at
  least two content terms *and* the required share of its own. One shared term is a coincidence —
  and for short messages, which have few terms to divide by, a single coincidence is 17%.
- **`MIN_PROPOSAL_TERMS` lowered 5 → 3.** Interjections and greetings still sit below it; a short
  real sentence no longer does.

**What this costs, measured.** Across the two transcripts, 8 of the 12 decisive turns now propose,
against 6 before. The "cheap path" — messages that pass without a question — is narrower than
revision 1 hoped: it now covers only messages that genuinely share vocabulary with the subject.
That is the correct side to err on given what a silent miss does, but it does mean a small extra
request, and its latency, on most turns where the subject drifts. `PROPOSE_COVERAGE` and
`MIN_SHARED_TERMS` are the two levers, and both are named here so that raising them later is a
decision with a record rather than a quiet edit.

**The pattern worth noticing.** Two thresholds have now been corrected, and both times the
reasoning behind the previous value had felt conclusive. Revision 0 was fitted to invented
replies that echoed; revision 1's floor was chosen from a table of exchanges that contained no
short real sentence. Neither error was findable by thinking harder about the same material — both
took a real conversation. That is the argument for the corpus being the thing that gets grown, not
the reasoning.

**Revision 2, addendum — the confirmer also names the topic it did not split.**

The third real conversation (`docs/eval/topics-2026-09-14-run3.json`) passed every boundary
judgement, including the two sentences that broke revision 0 and the two revision 1 never asked
about. It is also the first run in which **`confirmed: kept` was observed** — until then the
confirmer had only ever been seen opening a topic, never refusing one. Five of its turns were
kept, and all five were right.

It exposed one defect, and it was a naming defect rather than a boundary one. Four of the five
topics carried a noun phrase from the model; the fifth — the project topic — was called
「我在做 HDD 这个终端项目，数据库用的是内置的…」, a truncated user sentence. The cause: that topic
began with 「你好」, which is too thin to name anything, so its title stayed provisional; the next
substantive message was answered `same`, and the only name available on that path was the message
itself.

Since a greeting opens most sessions, this would have been the normal outcome rather than an edge
case. The fix costs nothing: the confirmation request is made anyway, so it now returns a name on
**either** answer — the new topic when the subject changed, the current topic when it did not —
and a provisional title takes it. A locked title is still never touched, and a name that is empty,
punctuation-only, or the placeholder is rejected in favour of the derived one. Covered by
`conversation.test.cjs` §11b; the recorded run predates the fix, so the corpus keeps what actually
happened and does not assert the name the model would now produce.

**Alternatives rejected**

- *A second request just to name the topic*: unnecessary, since the confirmation already carries a
  conversation summary and the answer is one JSON field.
- *Naming the first topic from a derived message and leaving it*: that is the defect above, and it
  produces names like a truncated sentence in the one place the user reads names.

## ADR-013 — Long-term memory: a triggered extractor, superseding rows, and a visible memory

**Status:** Accepted

**Context**

Phase 3 is "structured, updatable memories linked to the messages they came from" (ROADMAP). Most of
the shape was already fixed by earlier decisions and is not open here: memories live in the same
SQLite database — that need is *why* SQLite was chosen (ADR-002) — they arrive as migration 5
(ADR-004), they carry stable application ids and UTC timestamps and link to messages by foreign key
(ADR-005), and the main process owns them (ADR-001). ADR-007's deferred table also settles a
question that would otherwise dominate this phase: **no retrieval layer**, because "recent-N plus a
profile covers Phase 1–3".

Three things were genuinely open, and each had a cheaper option that this repository has already
seen fail or has already measured:

1. **Who writes a memory, and when.** Asking the model to extract after every turn doubles the
   request count, and v0.2 measured what that costs: a second request on 10 of 15 turns in one real
   conversation. But letting a local rule decide *what* is worth remembering repeats the mistake
   ADR-012 documents — a lexical rule asked a semantic question, and got it wrong about half the
   time in production.
2. **What "updatable" means.** Overwriting a memory is simpler, and loses the fact that it changed.
3. **Whether the user can see and correct memories.** Nothing in the phase description requires it.

**Decision**

**1. The local rule decides *when* to ask; the model decides *what* to remember.**

A cheap local trigger runs on every turn and costs no request. Only when it fires is one extraction
request made, and that request is what produces memories — it receives the turn's messages and must
return, for each memory, which of those messages it came from. Nothing is invented locally: if the
trigger fires and the model finds nothing worth keeping, nothing is stored.

The trigger's thresholds are named constants in `app/memory.js`, exported, and tuned against
`docs/eval` exactly as `app/topics.js`'s are — including the rule that a local judgement about a
semantic question is only ever allowed to *propose*. A turn where the trigger does not fire costs
nothing and stores nothing, which is a deliberate bias: a missed memory is a smaller loss than a
wrong one.

**2. Updating supersedes; it never overwrites.**

A memory is a row with a status and a link to the row that replaced it. A correction appends a new
memory and marks the old one superseded, so what she used to believe, and when that changed, stays
readable.

**`/forget`, by contrast, deletes.** A user asking her to forget something is asking for the text to
be gone, not for it to be quietly flagged; keeping it would be a betrayal dressed as traceability.
The two operations are deliberately different — automatic correction tombstones, an explicit
instruction removes — and the distinction is stated here because it is exactly the kind of thing
that gets silently unified later by someone tidying up.

**Forgetting removes the whole supersession chain, not one row.** A chain is one fact at successive
moments, so `A ← B ← C` is a single belief that was corrected twice. Deleting only `C` would leave
`B` pointing at a row that no longer exists — and because a memory is active exactly when nothing
supersedes it, clearing that pointer would quietly make `B` active again, restoring the belief the
user just asked to be rid of. The self-reference on `superseded_by` is declared as a foreign key for
this reason: the database refuses the half-deletion, so the mistake is a loud error rather than a
resurrected fact. Forgetting a middle row is allowed and takes only what came before it; the newer
belief survives untouched. Source links cascade with each row.

**3. `/memories`, `/forget` and `/remember` are in scope.**

A wrong memory is worse than no memory: it is the program asserting a false fact about the user,
which is the behaviour ADR-009 exists to forbid. So memories must be visible and removable by the
person they are about, with their origin shown. `/remember` lets the user state one directly, with a
source of "the owner said so" rather than a message it was inferred from. All three reuse the
existing `.line` elements: no CSS, no layout change, same as the topic commands.

**Consequences**

- **The capability declaration must gain a memory entry.** `capabilities.js` declares `chat` and
  `time` and mentions memory nowhere. ADR-009's rule — a capability that exists in the code must
  appear in that list — applies the moment she can say "I remember you said…". The cross-check test
  that enforces this is extended with it, so the declaration and the build cannot drift apart.
- **Injection is a budgeted selection, not a search.** Active memories render beside the profile,
  because they are facts about the owner; the section is capped, and ADR-008's warning about the
  prompt budget applies. Which memories lose out when the cap bites is a question for `docs/eval`,
  not for a comment.
- **A new failure mode to measure: misattribution.** She can now be wrong in a way she could not be
  before — not inventing a fact, but attaching a real memory to the wrong occasion, or stating as
  something the owner said what was in fact inferred. Provenance in the prompt is the mitigation;
  the evaluation set is how it gets checked, because ADR-010 names "did the memory extractor pick
  the right fact" as a tuning problem rather than an assertion.
- **The evaluation set grows a memory dimension**: a `docs/eval` entry of kind `memory`, recording
  the facts that should have been extracted from each turn, replayed by the same harness that
  already replays the topic conversations.
- **The cost is real and bounded**: one extraction request per triggered turn, on top of ADR-012's
  boundary request. Both are triggered rather than unconditional, and both are the price of
  deciding instead of guessing.

**Alternatives rejected**

- *Extract on every turn*: doubles the measured cost of ADR-012's own request, for turns where
  nothing memorable happened — which is most of them.
- *Extract locally, without the model*: ADR-012 is the evidence that a lexical rule cannot answer a
  semantic question. It proposed boundaries wrongly about half the time on the first real
  transcript.
- *Overwrite on update*: cheapest, and it destroys the only thing that makes a wrong memory
  trustworthy — being able to see that it was corrected, and from what.
- *Delete on update*: a superseded memory is evidence about the extractor, and the evaluation set
  needs it. `/forget` remains available when the user wants something gone.
- *Retrieval over memories now*: explicitly deferred by ADR-007's table, whose stated condition is
  that recent-N plus a profile covers Phase 1–3. Revisit when volume makes that false.
- *A memory panel or list UI*: the same reasoning as the topic panel in ADR-012 — three commands
  cover it, and a panel is a visual design for a verified fullscreen layout.
- *Free-text memories with no source links*: cheaper to write, and it removes the one property the
  phase description explicitly asks for. Provenance is the feature.

**Implementation order**, recorded because each step is verifiable on its own: migration 5 and the
store layer with tests first; then the extraction path; then prompt injection with the budget; then
the three commands; then the capability declaration and its cross-check; then the memory evaluation
corpus.

## ADR-014 — Projects: an owner-named container, and context assembled from it

**Status:** Accepted

**Context**

Phase 4 is "context assembly and projects; topics linked to projects" (ROADMAP), and until this
record that row was the whole of the specification. The surroundings are already fixed:

- the main process owns the state and the renderer only draws it (ADR-001);
- a schema change is **migration 6**, appended and never edited (ADR-004);
- `projects` gets an application-generated id and UTC timestamps, and a topic's link to it is a
  foreign key (ADR-005);
- `topics.project_id` must be **nullable** so the migration stays additive, the same requirement
  ADR-006 made for `topic_id`;
- no embeddings, no retrieval layer — "recent-N plus a profile" is the context policy until Phase 5
  decides otherwise (ADR-007) — and the prompt budget is a real constraint (ADR-008).

What exists today is one topic at a time: persona → capabilities → profile → memories → time, then
the active topic's last 30 messages, and switching topics swaps that history. Nothing spans topics.
The cost is recorded in the evaluation corpus: asked 「那个终端项目的全文搜索做到哪一步了」 she
answered 「主人，我这边没有你项目的进度记录」, in a conversation where the same project had already
been the subject of several topics (`docs/eval/topics-2026-09-14-run3.json`). Each topic was right in
isolation; the conversation had no unit above it.

Four questions were open:

1. **What is a project** — a container the owner fills, or a classification the app infers?
2. **What does it contribute to the prompt**, and does it replace the topic's history?
3. **Where does that contribution live** — stored, or derived at assembly time?
4. **How is it driven**, given one input line and no chrome? (ADR-012 answered that with commands.)

**Decision**

**1. A project is a container of topics that the owner names and fills. Membership is explicit.**

Migration 6 adds `projects` (`id`, unique `name`, `created_at`, `updated_at`) and a nullable
`topics.project_id` with an index. **Nothing is backfilled**: a project is an act, and inventing one
for existing topics would repeat the mistake ADR-006 rejected for topics — a store that never used
the feature would carry a fake row.

Commands, on the existing input line and printing through the same `.line` elements (no CSS, no
panel): `/projects`, `/project` (status), `/project new <name>`, `/project <number|id>`,
`/project off`. `/project new` assigns the current topic as well, because creating a project and
then putting nothing in it is not a use case.

A name is whitespace-collapsed and capped at 40 characters; a longer one is refused rather than
truncated, because v0.4 has no rename and the name is reprinted in the prompt header on every turn.

No inference, no model call, no keyword rule. ADR-012 is this repository's evidence that a lexical
rule cannot answer a semantic question, and the model is not asked either: a wrong assignment is
**silent** — it changes what she is told on every turn — and there is no ground truth to score it
against. The owner already knows which project they are in; one command states it. **The cost is
stated plainly:** every new topic inside a project needs that one command, and a boundary inside a
project does not inherit membership. That cost is the first thing to measure against a real
workload.

**2. A project contributes facts, never a generated summary.**

When the active topic belongs to a project, the system prompt gains one section between the memories
and the time:

```
# 当前项目：HDD
当前话题属于主人建的项目「HDD」。项目里的其他话题（新到旧）：
- 数据库选型（12 条）
- 发布打包（8 条）
这个项目里最近的其他对话（供参考，不是当前话题的内容）：
【数据库选型·主人】…
【数据库选型·你】…
```

Every line is read out of the store: the name, the project's other topics with their message counts,
and the most recent exchanges from those topics. The app does not summarise the project and the
model does not write a brief. A generated summary is a claim about the owner's work that the app
cannot verify — the failure ADR-009 forbids for capabilities and ADR-013 avoids for memories — and
it would cost a request per update.

**3. It is derived at assembly time; there is no context table.**

The block is computed from `topics` and `messages` on each turn by `conversation.messagesFor`. A
stored copy would be a second source of truth for the same rows and would drift the first time a
topic was absorbed or a message edited. This amends the ROADMAP's "context tables" expectation:
v0.4 adds no such table, and the reason is recorded here rather than left as an omission.

**4. The topic remains the unit of history; the project block is additive and bounded.**

The block does not replace the 30-message window and is not inserted as chat turns. The current
exchange is still the current topic's history (ADR-012); the project block is *reference* — labelled
as other topics' content so it cannot be read as something said in this one. Three ceilings keep it
inside the prompt budget (ADR-008): `PROJECT_TOPIC_LIMIT` (8 topics), `PROJECT_MESSAGE_LIMIT`
(6 messages) and `PROJECT_SECTION_MAX_CHARS` (1000 characters, plus 200 per excerpt). The section is
omitted entirely when the active topic has no project.

**5. It costs no request, and declares no new capability.**

v0.4 adds no API call: membership and context are local. The capability list is unchanged — a
project is context the app stores, not something she can do. The `memory` entry already covers
"remembers some of what the owner said", and this phase does not make its wording more specific.

**Consequences**

- Migration 6 is additive and leaves every existing topic unassigned. A v0.3 store opens at v6 with
  no project rows.
- `absorbTopic` carries the project with the messages: when a provisional (greeting) topic is merged
  into the topic that replaced it, its `project_id` moves to the surviving topic. Membership follows
  the messages the owner assigned.
- Existing prompt-order assertions still hold; the project section sits between memories and time.
- **A new failure mode to measure:** she may read a sibling topic's excerpt as something said in the
  current exchange. Explicit labelling and the excerpt ceiling are the mitigation; whether that
  works is a question for the next real conversation, not for an assertion.
- Project assignment is deterministic, so it adds nothing to `docs/eval` (ADR-010 covers model
  judgements). `/projects` is covered by store, conversation and renderer tests instead.
- **Nothing can delete or rename a project in v0.4.** An empty project is harmless and visible; a
  destructive command with no confirmation is not. Recorded as a debt rather than shipped.
- `inspect.cjs` has no project view of its own. `--prompt` shows the project block because it now
  goes through the same assembly path, but a project that no current topic points at is invisible
  there; like memories before it, that is the audit tool's next blind spot.

**Alternatives rejected**

- *Let the model assign the project during the boundary confirmation*: it would cost no extra
  request — the confirmation already runs and already names things — but it adds a silent
  wrong-assignment failure mode for a decision the owner can make in one command. Revisit when a real
  workload shows the curation cost is what stops the feature from being used.
- *Inherit the current topic's project when a boundary opens a new topic*: convenient, and wrong in
  the same way — the project would follow the subject wherever it went, including away from the
  project. `/project <n>` states the intent instead.
- *A local keyword rule for assignment*: ADR-012's measured failure, repeated on a new question.
- *A model-written project brief or summary*: a request per update, and it asserts project status
  the app cannot verify.
- *Store the assembled context in a table*: a second source of truth for the same rows.
- *Merge a project's topics into one history*: it would undo topics, whose subjects are deliberately
  separate.
- *A project panel or sidebar*: the same reasoning as every other panel here — a visual design for a
  verified fullscreen layout, for a feature five commands cover.

**Implementation order**, recorded because each step is verifiable on its own: migration 6 and the
store layer with tests first; then prompt assembly with the three ceilings; then the commands and
the IPC cross-checks; then the docs and the debts.

## ADR-015 — A room, not a printer: the boundary, the two registers, and delegation

**Status:** Accepted (2026-10-28)

**Context**

Phases 1–4 built a relationship, not a workbench: topics, memories with provenance, projects, a
persona and a mascot that changes state. None of that is needed to edit code. Phases 5–9 as the
roadmap wrote them drifted the other way — files, tools, agent runs — and the owner asked what HDD
is actually for. The confusion was real and the roadmap carried it: the next four phases described
a smaller harness, while the first four phases had built a room.

Part of the answer was already fixed by verified design. The renderer folds every newline into a
space, puts one reply on one visual line, uses no bubbles, and fades history toward the mascot.
HDD **cannot** display a document by construction; that was a deliberate look, not a missing
feature. And the app already has two registers: conversation, and command output — `/topics`,
`/memories`, `/projects` and `/search` print structured lists, and have since v0.2. Long content
already has a home; the question was which register it belongs to.

Delegation was measured rather than assumed, on 2026-10-28:

- `dsh --profile headless "<task>"` exists: one task in, one final assistant message out, exit.
- It boots only when `DEEPSEEK_API_KEY` is exported to the child. Without it the launcher fails
  with `MISSING_CREDENTIAL` and names the harness credentials service — so a handoff must carry the
  key through the environment, not assume the GUI's stored credentials are reachable.
- It attempted shell commands **without any approval prompt**, and under this configuration the
  shell tool itself failed twice: first `Windows ACL temp root must be outside the workspace`, then
  `spawn C:\Program Files\PowerShell\7\pwsh.exe ENOENT`. It reported the failure honestly instead
  of claiming success.

So the interface exists, it is not turnkey, and its failure arrives as an ordinary-looking final
message: the caller must read the output, not merely note that the process finished. That is the
same shape as the v0.2 defect this project already paid for.

**Decision**

**1. HDD is a room, not a printer. Her subject is the owner's reading, notes, projects and personal
facts — not the owner's codebase. Execution belongs to the harness.**

Non-goals, stated as firmly as the goals: no code editing, no builds, tests or git, no multi-step
agent orchestration, no diff or approval UI, no panels. The test for any future feature is one
question — **is its deliverable a work artifact, or is it continuity and conversation?** A patch,
a build, a report belong to the harness. Remembering, discussing, proposing and pointing belong
here.

**2. Two registers, and a drawer for everything long.**

- **Conversation** is a short explanation, the length of ordinary conversation: typically 2–5
  sentences, enough to explain one thing, never a wall; no lists, no headings, no code blocks. The
  existing newline folding stays. The default is a tunable constant (`REPLY_SOFT_LIMIT`, starting at
  about 240 characters), not a taste, and it is adjusted from real conversations the same way the
  topic and memory constants are.
- **Commands** may be structured. That is already true (`/topics`), and it stays true: a list is
  something the owner asked for, not something she volunteers.
- Anything longer than the speech budget becomes either **a follow-up turn** the owner asks for
  ("展开" / "继续") or **a file**. It never becomes a wall of chat text.

A corollary that keeps ADR-009 honest: files HDD writes are **its own artifacts** — handoff briefs,
reports — under its data directory. That is app state, not the owner's files. Reading the owner's
imported files (Phase 5) and modifying the owner's files remain separate capabilities, and the
latter stays absent until Phase 9's export.

**3. Execution is delegated, never inferred.**

HDD may **propose** a handoff. The owner confirms. The approval step is a person, not a classifier,
for three reasons that are not hypothetical: a wrong route changes the owner's files; imported
documents make prompt injection a real path from a PDF to a shell; and ADR-012 already measured how
often a semantic classification misses.

- **L1 — the brief.** `/hand <need>` composes a self-contained brief from the conversation, memories,
  project and library, writes it to `data/handoffs/<timestamp>.md`, and says one line: where it is
  and whether to send. Nothing is printed for copying, because the owner does not want to paste.
- **L2 — the send.** After confirmation, HDD spawns `dsh --profile headless` with the brief as the
  task, a configured working directory, a timeout, the key injected into the child environment, and
  a record of the task text, start, end, exit code and output. The result comes back as at most
  three lines plus a file for the full log.
- **L3 — automatic routing.** Deferred until L2 has measured usage and a permission model exists
  (Phase 6). It is not a v0.5 feature and it is not a default.

The brief is shown **before** it is sent. That is the human firewall: an instruction hidden in an
imported document has to appear in plain text in the brief for the owner to approve it. No
retrieved content may become a task without being visible there.

**4. The handoff is recorded, and a failure is reported as a failure.**

A handoff is an action with side effects, so it gets the same treatment as every other entity here:
an application-generated id, UTC timestamps, and a stored outcome. An uninstalled harness, a
timeout, a non-zero exit and a hung approval are all "it did not run", never a success message.
The headless measurement above is the evidence that this is necessary: the tool can fail while the
model writes a perfectly calm paragraph about it.

**Consequences**

- The roadmap changes: Phase 5 is reshaped by ADR-016; Phase 6 narrows to a few safe local actions
  plus the handoff audit, not a tool platform; **Phase 8 (agent runs) is removed as a phase**,
  because execution is delegated.
- The capability list gains "把自己的简报写成文件" (app state) and, in Phase 5, "读主人导入的文件".
  "不能修改或删除主人电脑上的文件" remains true.
- A handoff record needs storage: a table appended after Phase 5's migration 7, or a `meta`-keyed
  record — decided when the protocol is implemented, with the same rules as every other entity.
- New failure modes, with their mitigations: a handoff that runs when it should not (confirmation
  plus a visible brief); a task that fails quietly (exit code, stderr, audit row); a result too long
  for the room (the three-line contract, full log in a file).
- The reply budget is measurable: the distribution of reply lengths in `docs/eval` is the dataset,
  and "she never gives a wall of text" becomes an assertion the page tests can check.

**Alternatives rejected**

- *Replace the harness or build its tools*: asymmetric competition on its home turf, with none of
  its infrastructure, and it would bury the character under tooling.
- *A panel or document view for long answers*: contradicts the verified fullscreen composition and
  turns the room into a workspace. The drawer already exists — commands and files.
- *Let the model decide when to hand off*: cheap to write, and the error is an action on the owner's
  files. ADR-012 is this repository's evidence that the semantic judgement is the unreliable part.
- *Print the brief and let the owner paste it*: solves nothing the owner asked to solve. A file is
  the same artifact without the clipboard.
- *Keep long answers in chat and trust the fade mask*: the mask protects the composition, not the
  immersion. A wall of text is still a wall.

**Implementation order**, each step verifiable on its own: the reply-length constant and the
"展开" rule first (prompt and page tests, no integration); then the brief file and its contract
(L1, judged by whether the owner ever sends one); then the L2 spawn with audit and failure
semantics; then the capability declarations and the documentation.

## ADR-016 — Phase 5: the owner's library, notes first, PDFs later

**Status:** Accepted (2026-10-28)

**Context**

The roadmap row said "Files and chunks; chunking, embeddings, semantic retrieval", with tables
`files`, `chunks`, and the vector-store decision due at the start (ADR-007). That was the whole of
the specification.

Four measurements changed the shape:

1. **DeepSeek has no embeddings endpoint.** On 2026-10-28, `GET /models` listed only
   `deepseek-flash` and `deepseek-v4-pro`; `POST /embeddings`, `/v1/embeddings` and
   `/beta/embeddings` all returned 404, while `/v1/chat/completions` returned 200 — so the `/v1`
   prefix is mounted and the route is genuinely absent. Embeddings require a second provider, or
   the mechanism changes to lexical retrieval plus reranking.
2. **The owner's corpus lives in Zotero, and it is richer than the PDFs.** On 2026-10-28 the local
   library reported 620 items: 35 papers (journal articles, conference papers, preprints and a few
   reports/documents), 29 Chinese notes of 11–14k characters each, 521 highlights, and 35 PDF
   attachments. A highlight
   is already an exact English sentence, a page label (`45:15`) and the owner's Chinese comment; a
   note is a long Chinese summary. That is the highest-signal, zero-parsing corpus in the library.
   A full PDF is lower signal and much more work: two columns, equations, references, headers.

3. **Zotero exposes that library over a local, keyless API.** Zotero 10.0.6 answers at
   `http://127.0.0.1:23119/api/users/0` (measured 2026-10-28: 200 OK, 620 items, library version
   1001, schema 44, **no key**). It serves notes as HTML, annotations with `annotationText`,
   `annotationComment` and `annotationPageLabel`, papers with title/authors/date/abstract, and
   attachment metadata. That removes the export step entirely and keeps the data on this machine.

4. **A provider candidate was measured, not selected.** On 2026-10-28, SiliconFlow's `BAAI/bge-m3`
   answered in 327 ms at 1024 dimensions (90 tokens for six short texts). A Chinese-query ×
   English-passage sanity matrix separated a direct match (0.804) from unrelated pairs (0.32–0.40),
   but a conceptual query's correct passage beat the wrong one by only 0.032 (0.584 vs 0.552). The
   model is viable; the thin margin is why ranking and the evaluation set decide, not a guessed
   threshold. The real library was then embedded with it: 1386 chunks in 17.7 s, and `/recall`
   returned the target papers and notes at 0.71–0.62. That is evidence the model works, not a
   threshold; the evaluation set still decides where injection starts.

The need is cross-lingual: ask in Chinese, answer from the English original. The owner asks about
the original more often than about the note, so the retrieval must reach English text and must say
which it reached.

**Decision**

**1. Phase 5 reads the Zotero local API directly. Export is the fallback, not the path.**

`/zotero sync` fetches papers, notes, highlights and attachment metadata from
`http://127.0.0.1:23119/api/users/0`, groups them by parent item, and stores one row per paper.
A highlight's parent is its PDF attachment, so attachment metadata is fetched first to map each
annotation back to the paper. `/file add <path>` remains for plain text and Markdown, and for an
export when Zotero is not running. This proves "ask in Chinese, answer from the English original"
without a parser, OCR, or a third API key. **PDF full text is the second step**, gated on that
proof.

**2. PDFs are text-layer only in this phase, and bad extraction is visible.**

Scanned PDFs are refused with a sentence rather than sent to OCR. Two-column reconstruction is
best-effort. `/file show` prints the extracted text and the chunk count, so a garbled import is seen
and removed, not silently indexed. This is the ADR-009 shape applied to extraction: the app may say
"this is what I read", never "I read it" when it did not.

**3. The schema is migration 7, additive, and small.**

`files` (id, name, kind `paper|note|other`, lang, source `zotero|file`, zotero_key UNIQUE, title,
item_type, year, creators_json, tags_json, zotero_version, source_path, bytes, sha256, content,
created_at) and `chunks` (id, file_id → files, ordinal, kind `abstract|note|highlight`, page, text,
start_offset, end_offset, embedding BLOB, embedding_model, created_at). One `files` row per paper;
its content is the assembled abstract + notes + highlights, and its chunks carry the kind and page
so the prompt can label a quote as a highlight rather than a summary. Content is copied into the
store; the path is provenance only. A chunk stores the model that embedded it, so vectors from
different models are never compared. No `chunks_fts` in the first cut; the seam stays open for
hybrid retrieval.

**4. Embeddings come from a second provider behind a provider-agnostic client.**

Config gains `embeddingBaseUrl`, `embeddingApiKey`, `embeddingModel` (environment wins, as usual).
DeepSeek cannot serve this (measured). The provider is **not fixed here**: the candidates are a
multilingual model (BGE-M3 class) and a Chinese provider's multilingual endpoint, and the choice is
made by the evaluation set in point 6, not by a specification sheet. If no provider is acceptable,
the fallback is chunk-level FTS5 plus model reranking — ADR-007's third option — and the roadmap
wording changes with the reason recorded.

**5. Retrieval has two entries, and the section is labelled by source.**

`/recall <描述>` is explicit and changes no prompt. Automatic injection happens only when a
**measured** threshold is cleared, is reference rather than history, and is bounded by count and
characters. Every excerpt says whether it is original text or the owner's note, and the prompt
forbids attributing a note to the paper. The owner asks about the original; the answer must not
quietly become a summary of their own summary.

A third entry is `/read <title|n>`: **one named document, injected whole for one turn** (or until
detached), bounded by a character cap, with no generated summary — the paper is the paper. This is
the answer to "帮我阅读一下这篇文献", which is a different operation from "find the passage about X".
If the document exceeds the cap, the app says so and points at `/recall` instead of pretending to
have read it.

**6. The evaluation set is written before the threshold.**

`docs/eval/retrieval-*.json`: 7 Chinese questions answered in English papers, 2 answered in Chinese
notes, 1–2 with English technical terms. Replayed by `probe --retrieval`, which prints top-k hits
and a threshold sweep. The model choice and the injection threshold both come from that file.

The first replay (2026-10-28, 11 positive and 2 negative questions over the real library) gave
hit@1 6/11 and hit@3 9/11. At **0.55** it kept 10/11 positives and produced **0/2 false positives**;
0.60 kept 9/11, and 0.65 collapsed to 2/11. 0.55 is the starting injection threshold, recorded as
`RETRIEVAL_INJECT_THRESHOLD`; one library is a start, not a corpus.

**7. Hybrid lexical plus vector retrieval is recorded, not built.**

Exact terms (`LoRA`, `DPO`) are where vector search is weakest and FTS5 is strongest. The retrieval
module keeps the seam; adding `chunks_fts` and a reciprocal-rank merge is a later, evidence-led
change.

**Consequences**

- `files` and `chunks` exist at schema v7; nothing is backfilled.
- Capabilities gain "读主人 Zotero 文献库里的笔记和高亮" and "从这些内容里按意思找片段". "不能修改或删除
  主人电脑上的文件" remains true; the Zotero API is read-only and writing stays out until Phase 9's
  export.
- **No third key.** The Zotero API is local and unauthenticated; only the embedding provider needs a
  secret. Zotero must be running for a sync, and an unreachable Zotero is a sentence, not a silent
  empty library.
- The first sync is a **full** sync: 35 papers, 29 notes and 521 highlights are small enough to
  refetch. `zotero_version` per paper makes an incremental pass possible later; it is not built
  until the full sync is shown to be slow.
- **The corpus is the owner's own reading and writing.** Embedding sends chunk text to a third
  party; that must be said plainly before the first sync, and a local-embedding fallback stays
  open. Nothing is sent before the owner has seen this.
- Changing the embedding model invalidates stored vectors. `embedding_model` per chunk makes the
  mismatch visible; a re-index is required and is not automatic.
- PDF parsing and OCR are **not** in this phase; full paper text is the next gate. Zotero live
  integration is in this phase, because it replaced the export path.
- The reply budget from ADR-015 applies to retrieval answers too: a hit becomes a sentence and a
  pointer, not a pasted excerpt.

**Alternatives rejected**

- *Export first*: the local API is live, keyless and already structured; an export is a manual step
  that goes stale the moment a note is edited.
- *Read `zotero.sqlite` directly*: an internal schema that changes between versions, and a database
  locked while Zotero runs; the local API is the supported surface.
- *Full PDF parsing first*: the largest and least verifiable work, before the value is proven.
- *Translate the papers into Chinese*: lossy, costly, and it removes the exact wording the owner
  asks for.
- *Translate the query and use an English-only embedding model*: an extra request and translation
  errors; a multilingual model does it in one step.
- *A Chinese-only embedding model*: fails the cross-lingual requirement by construction.
- *A separate vector database*: another process and another source of truth, for a personal library
  that brute-force cosine can serve.
- *Auto-inject everything above a guessed threshold*: this project has twice paid for thresholds
  chosen by reasoning.

**Implementation order**, each step verifiable on its own: the Zotero client and a full sync first
(a fake transport in tests, a real sync on this machine); then migration 7 and the store layer;
then the chunker for the three shapes (note paragraphs, highlight + comment, abstract); then the
embedding client; then `/zotero`, `/files` and `/recall`; then the measured threshold; then the
prompt section; then the capability declaration, `inspect` listings and the release.

## Architecture invariants

Short list, to be checked before any structural change:

1. The main process owns persistent state; the renderer displays it.
2. The API key never leaves the main process; the renderer has no network access
   (CSP `connect-src 'none'`).
3. Schema changes go through a migration; shipped migrations are never edited.
4. Timestamps are UTC; IDs are stable and application-generated.
5. The prompt never claims a capability the app lacks. Capability **facts** live in
   `capabilities.js` and reach the prompt every turn; the persona states the honesty rule but
   never restates the facts (ADR-009).
6. The font-weight override in `live.template.html` stays — removing it reintroduces the
   synthetic-bold blur described in README 7.1.
7. The fade mask stays on `#out`, never on `#log`.
8. Published artifacts never contain a real API key or a redistributed font.
9. Topic membership and the active topic are decided in the main process; the renderer may only
   ask for a topic, switch to one, or name one (ADR-012).
10. A memory is never overwritten. Corrections supersede and keep both rows; only an explicit
    `/forget` removes one, because the user asking is different from the app correcting itself
    (ADR-013).
11. A topic belongs to at most one project, and membership changes only on an explicit command.
    Project context is derived from the stored rows at assembly time; it is never a generated
    summary and never a second copy of the data (ADR-014).
12. The conversation register stays short. A long answer is a follow-up turn, a file, or a
    command's structured output — never a wall of chat text (ADR-015).
13. Execution is delegated, never inferred: HDD may propose a handoff, the owner confirms, and
    every handoff is recorded with its outcome (ADR-015).
14. Every retrieved chunk is labelled as original text or the owner's note, and the prompt never
    attributes a note to the paper (ADR-016).
